## Issue #2: pin Node 24 and add typecheck and validate npm scripts

Plan reference: section 6, Phase 1, steps 1 and 2. Branch `chore/issue-2-node-and-scripts`, delivered as a pull request rather than a direct commit to `main` (see "Left out of scope").

### Changed

| File | Change |
|---|---|
| `.nvmrc` | new, contains `24` |
| `package.json` | `lint` is now `eslint .`; new `typecheck` (`next typegen && tsc --noEmit`) and `validate` (`npm run typecheck && npm run lint`) |

### Verified

- `npm run validate` exits 0 with `.next/` removed first. `next typegen` prints "Types generated successfully", `tsc` and `eslint .` print nothing.
- `.next/types/` exists afterwards with `routes.d.ts`, `root-params.d.ts`, `cache-life.d.ts`, `validator.ts`.
- Fresh-clone simulation: with `.next/` and the gitignored `next-env.d.ts` both removed, `tsc --noEmit` alone fails with `TS2304: Cannot find name 'LayoutProps'` in `app/layout.tsx`. `npm run typecheck` then passes and recreates `next-env.d.ts`. This is the reason `typegen` runs before `tsc`.
- `git status` after the run shows only the two intended files. `AGENTS.md` is untouched (`next typegen` does not write the agent block; that check belongs to `next dev` in issue #3).

### Review pass

**1. Error and empty states.** The scripts have four reachable failure states, each of which prints what to do next:

- `next` not found: `npm ci` has not run. npm prints `sh: next: command not found`. Next step: `npm ci`.
- `next typegen` fails to load `next.config.ts`: the error names the config file. Next step: fix the config.
- `tsc` reports type errors: file, line, and TS code are printed. Next step: open the file.
- `eslint .` reports violations: file, line, and rule name are printed. Next step: open the file.

`.nvmrc` has no failure state. Without nvm it is ignored and the system Node runs. Nothing reachable from this change leaves the user with nothing to do.

**2. Type fields rendered by the UI.** Not applicable. This sub-issue adds no types and touches no UI. The only type in play is Next's generated `LayoutProps<"/">`, consumed by `app/layout.tsx` unchanged.

**3. Permission gates per route.** Not applicable. The site has one route, `/`, prerendered static, with no service calls and no authentication. Nothing in this sub-issue adds either, and the plan keeps it that way (section 1, out of scope: backend, form submission).

## Issue #3: make next.config.ts agent-safe

Plan reference: section 6, Phase 1, step 3. Branch `chore/issue-3-agent-safe-next-config`, delivered as a pull request.

### Changed

| File | Change |
|---|---|
| `next.config.ts` | `experimental` is now `{ agentFeedback: false, agentUpgrade: false }`. `cacheComponents`, `partialPrefetching`, and the `turbopack` `*.css` rule are unchanged. |
| `documents/plans/2026-10-08-builder-landing-page-plan.md` | One sentence about `agentRules` corrected (see review pass, item 4). |

### Verified

- `npm run validate` exits 0. `tsc` accepts `agentUpgrade: false`; the type in `node_modules/next/dist/server/config-shared.d.ts` is `'security' | 'latest' | 'experimental-future' | false`.
- `npm run dev` started in a terminal where the `CLAUDECODE` environment variable is set (so Next sees a coding agent), served `GET /` with 200, and was stopped. The dev log lists `agentUpgrade` under "Experiments" because it is no longer at its default, and shows no font or config error.
- `AGENTS.md` is byte-identical before and after the run (checked with `diff`). `git status` shows only `next.config.ts`.
- Not verifiable locally: that `agentUpgrade: false` prevents a stop in Builder's sandbox. No security advisory applies to Next.js 16.4.0 today, so the default `security` policy would not have stopped the server either way. The setting is defensive; the docs say `false` "disables upgrade reminders", which is the mechanism that stops an agent-run `next dev`.

### Review pass

**1. Error and empty states.** The change removes two states rather than adding any:

- With `agentFeedback: true`, an agent-run `next dev` with telemetry on would add a feedback block to `AGENTS.md`, dirtying the tree in Builder. Gone.
- With `agentUpgrade` at its default, an agent-run `next dev` could stop with upgrade instructions when an advisory applies, so the Builder preview would never come up. Gone.

One reachable state remains: if `next.config.ts` fails to load, `next dev` and `next typegen` print the error with the file name, and the next step is to fix the config. Nothing leaves the user with nothing to do.

**2. Type fields rendered by the UI.** Not applicable. No types or UI changed. The config object's fields are consumed by Next, not rendered.

**3. Permission gates per route.** Not applicable. Still one static route, no service calls, no auth. Turning off two dev-time agent features adds neither.

**4. Doc sentences read while editing, and whether they are still true.**

- Plan, section 6 facts, and issue #3 body: "`agentRules` stays on; its block is already committed and only rewrites when missing." Imprecise. `upsertAgentRulesBlock` in `node_modules/next/dist/server/lib/generate-agent-files.js` replaces the text between the markers whenever it differs from the installed version's block and leaves the file alone when it matches. So the block is rewritten after a Next.js upgrade, not only when missing. **Fixed in the plan** in this pull request. The same sentence in the issue #3 body is left as written because the issue closes with this pull request.
- Plan, section 6 facts: "`next dev` with `experimental.agentFeedback: true` appends a feedback block to `AGENTS.md` whenever it detects a coding agent": true, with two conditions the doc adds and the plan omits: Next.js telemetry must be enabled, and it does not run in CI. Not changed; the plan's conclusion (turn it off) holds either way.
- Plan, section 6 facts: "`experimental.agentUpgrade` (default `security`) can stop `next dev` with exit code 1 when an agent is detected and an advisory applies": the doc says "the first eligible reminder stops the command with instructions to report the upgrade" and does not name an exit code. The behaviour matches; the exit code is unverified and left as written.
- `agentFeedback.md`: "It is disabled by default" and "New apps created with the recommended `create-next-app` settings enable agent feedback in the generated Next.js config": both true, the scaffold had it on.
- `agentUpgrade.md`: "`false` disables upgrade reminders": true per the type and the dev log.
- `agentRules.md`: "The next `next dev` run removes the existing agent rules block" applies only when `agentRules` is set to `false`, which this change does not do. True, not relevant.
- `AGENTS.md` managed block: "Removing it from a diff only re-creates the uncommitted change; committing it with your work keeps the tree clean": true, the block stayed committed and the run produced no diff.

One sentence fixed (the plan's `agentRules` sentence). Everything else read was true.

**5. Left out of scope.**

- `agentRules: false`. The plan keeps it on so Builder's agent reads the bundled Next.js 16.4 docs. Cost to turn off: one line, and the next `next dev` would delete the managed block from `AGENTS.md`, which is a diff in Builder.
- Disabling Next.js telemetry (`next telemetry disable`). It would also stop the feedback block, but it is a per-machine setting, not a repo setting, so it would not carry into Builder's sandbox. Cost: one command per machine, no benefit here.
- `allowedDevOrigins`. The plan defers it to the Builder boot check in section 7 because the hostname is unknown until the preview runs. Cost now: one line once the hostname is known.
- Editing the issue #3 body to match the corrected plan sentence. Left alone because the issue is the historic spec and closes on merge. Cost: one `gh issue edit`.
