### Review pass

**1. Error and empty states.** The file is a constant with no branches, so every state it can reach is a compile-time one, and each names the next step:

- Moving or renaming the file: `tsc` fails every importer on the unresolved `@/content/site` specifier, with file and line. Nothing imports it yet.
- Assigning through the config (`siteConfig.cta.label = ...`) or calling `siteConfig.nav.push(...)`: `tsc` reports the property or method as read-only, naming it. Next step: spread into a new array or object, as the footer (#27) does to add its fifth link.
- Passing `siteConfig.nav` where a mutable `{ label: string; href: string }[]` is expected: the TS2345 error measured above, which prints both types. Next step: `readonly` on the parameter, which #24 and #25 specify and the plan's section 3 table now says.
- An empty `nav`: not reachable from this file. The value is a literal with four entries and its type is a four-element tuple. `NavLinks` (#24) will accept any `readonly NavItem[]`, where an empty array would render an empty `<ul>` inside a labelled `<nav>`; that case belongs to #24's review.

### Review pass

**1. Error and empty states.**

- A `tone` outside the map: `tsc` rejects it and prints the four-member union, because the prop type is `keyof typeof tones`. A JavaScript caller could still pass one; `tones[tone]` is then `undefined`, `cn` drops it, and the band inherits the body's cream. Next step is the type error. Nothing to fix.
- No `children`: a type error, since `children` is required. An empty fragment renders a band of padding, 192px tall at `sm`; that is a section file's bug, and the sections rule says every section opens with a `SectionHeading`.
- No `id`: no attribute is written, so the band is not a hash target. Correct for the hero and the closing call to action, which the nav does not link to.
- A `className` that overrides only one breakpoint of the padding (`py-8`): the base utility is replaced and `sm:py-24` survives, measured above. The JSDoc now tells a prompt to pass both breakpoints.
- The default-variant button on the espresso tone is espresso on espresso, visible by its cream text alone (screenshot). No plan section puts a button on the espresso band: Stats has none, and the footer's links are plain `<a>`s. If one is ever added, `variant="secondary"` (tan) or `"outline"` is the answer. Nothing to fix here.
- Focus on the gold tone: the espresso ring at 50% is 2.6:1 against gold and 2.9:1 against the espresso button, both under 3:1. A keyboard user still sees a ring, so the state is not "nothing", but it fails the WCAG non-text minimum. No gold section exists yet; the closing call to action (Phase 6) will put two buttons there. The fix is on the button pattern, not on `Section`: a full-opacity ring (`focus-visible:ring-ring`, 7.6:1 on gold) on the CTA links, or on every link styled as a button. Phase 2's note queued this for Phase 7 with the cream number; the gold number settles the direction. Left to Phase 6 and 7; cost in item 5.

Nothing leaves the user with nothing to do.
