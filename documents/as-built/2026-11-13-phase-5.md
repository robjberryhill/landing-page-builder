### The three choices the issue left open

| Choice | Used | Why |
|---|---|---|
| Blank strings | `hasText` from `lib/text.ts`. A blank `value` leaves out the value line, a blank `label` leaves out the label line, and with both blank the block returns `null`. | The same rule as `SectionHeading`, `BagLabel` and `FeatureCard`. A value cleared in the Visual Editor leaves its label standing, so the person editing can see what happened. |
| A very long word | `wrap-anywhere` on the wrapper | The utility the other blocks use. The first commit also had `min-w-0`, copied from `FeatureCard`'s inline variant, where the text sits in a flex child. The branch review asked whether a grid item needs it. Measured, it does not: `wrap-anywhere` alone gives the same result as the pair, and `min-w-0` alone fixes nothing (table under Verified). Removed. |
| The element | Two `<p>` elements, as the plan has it | See below. |

On the element. A `<dl>` puts the term first and its value second, so a stat would be read as "roaster to porch, on average: 48 hours", with the label before the number it explains. The page shows the number first, and showing it first in a `<dl>` means reordering with CSS so that the visual order and the reading order disagree. With two paragraphs a screen reader reads "48 hours" and then "roaster to porch, on average", which is the sentence as written. The accessibility tree for the grid is eight `paragraph` nodes, each with one text node, value before label, in the order of the array, and no other role. The first run printed four of the eight; the run after the branch review printed all of them.
