## Issue #43: add the Stat block

Plan reference: section 6, Phase 5, the `Stat` bullet; the `Stat` row in section 3; the component rules in section 5b. Branch `feat/issue-43-44-stat-and-stats`, shared with issue #44, delivered as a pull request.

### Changed

| File | Change |
|---|---|
| `components/site/stat.tsx` | new, 32 lines, Server Component. Exported `StatProps` (`value`, `label`), a JSDoc paragraph, and a wrapper `<div className="wrap-anywhere">` around two `<p>` elements: the value (`text-4xl font-semibold tracking-tight sm:text-5xl`) and the label (`opacity-80`, plus `mt-2` when a value sits above it). Two additions to the issue's sketch, both among the choices the issue left open: the blank-string rule and the wrapper's `wrap-anywhere`. |
| `documents/plans/2026-10-08-builder-landing-page-plan.md` | Phase 5, the `Stat` bullet: the wrapper classes, the blank-string rule and the note that the block sets no colour. Review pass, item 4. |

Nothing imports the block yet. `Stats` (#44) is its only caller, so `/` still renders the Phase 4 page.

### The three choices the issue left open

| Choice | Used | Why |
|---|---|---|
| Blank strings | `hasText` from `lib/text.ts`. A blank `value` leaves out the value line, a blank `label` leaves out the label line, and with both blank the block returns `null`. | The same rule as `SectionHeading`, `BagLabel` and `FeatureCard`. A value cleared in the Visual Editor leaves its label standing, so the person editing can see what happened. |
| A very long word | `wrap-anywhere` on the wrapper | The utility the other blocks use. The first commit also had `min-w-0`, copied from `FeatureCard`'s inline variant, where the text sits in a flex child. The branch review asked whether a grid item needs it. Measured, it does not: `wrap-anywhere` alone gives the same result as the pair, and `min-w-0` alone fixes nothing (table under Verified). Removed. |
| The element | Two `<p>` elements, as the plan has it | See below. |

On the element. A `<dl>` puts the term first and its value second, so a stat would be read as "roaster to porch, on average: 48 hours", with the label before the number it explains. The page shows the number first, and showing it first in a `<dl>` means reordering with CSS so that the visual order and the reading order disagree. With two paragraphs a screen reader reads "48 hours" and then "roaster to porch, on average", which is the sentence as written. The accessibility tree for the grid is eight `paragraph` nodes, each with one text node, value before label, in the order of the array, and no other role. The first run printed four of the eight; the run after the branch review printed all of them.

### Verified

Measured on a throwaway route, `app/stat-check/page.tsx`: the four real stats from section 4 in the stats grid (`grid gap-10 sm:grid-cols-2 md:grid-cols-4`) inside `<Section tone="espresso">`, a second espresso section with the edge cases, and one stat on cream. The route was deleted before the commit and never staged. A dev server for this repo was already listening on port 3000 (started outside this session), so this sub-issue used it and left it running. Measurements ran in headless Chrome 157 over the DevTools protocol with a dependency-free Node driver, after `document.fonts.ready`.

- `npm run validate` exits 0 after each throwaway route was deleted, including after the review fixes. `tsc --noEmit` and `eslint .` print nothing.
- Value at 1280 by 900: Bricolage Grotesque, 48px, weight 600, letter spacing -1.2px, line height 48px, `rgb(250, 245, 236)` (cream) on `rgb(42, 26, 18)` (espresso).
- Label at 1280px: 16px, weight 400, line height 24px, the same cream with a computed `opacity` of 0.8, and an 8px top margin.
- At 375 by 800 the value is 36px with a 40px line height and -0.9px letter spacing. The label is unchanged.
- Contrast, computed from the painted colours. The label blends to `rgb(208, 201, 192)` over espresso, which is 10.22:1. The value is 15.41:1. On cream the label is 8.36:1. All are above the 4.5:1 the issue asks for.
- Column widths in the stats grid: 242px at 1280px, 146px at 768px, 335px at 375px, each with a 40px gap.
- The longest real pair, "1" with "roast day a week. It is Tuesday.": one line at 1280px and 375px, two lines at 768px, with nothing clipped.
- At 768px, where the columns are narrowest, "48 hours" and "11 years" do not fit on one line at 48px. Each breaks at its space into two lines ("48" then "hours"), no word is split, and nothing overflows. "6" and "1" stay on one line, so the four labels start at two different heights in that row. This is the grid's concern and is passed to #44, which asks for exactly this check.
- A 45-character word as the value and a 54-character word as the label: both wrap inside the column at all three widths (five lines at 1280px, eight at 768px, three at 375px for the value). The wrapper's `scrollWidth` equals its width, and page `scrollWidth` equals the viewport at 1280, 768 and 375.
- The wrapper classes one at a time, on the sketch's markup with the 45-character value, added after the branch review:

  | Wrapper class | Page `scrollWidth` at 375px | At 768px |
  |---|---|---|
  | none (the issue's sketch) | 811 | 1068 |
  | `min-w-0` | 811 | 1068 |
  | `wrap-anywhere` | 375 | 768 |
  | both | 375 | 768 |

- Blank strings, read from the rendered HTML: `value="  "` gives the wrapper with `<p class="opacity-80">` alone, with no `mt-2` (with both present the label's classes are `opacity-80 mt-2`, joined by `cn` since the review); `label=""` gives the value paragraph alone; `value=""` with `label=" "` renders nothing.
- On cream both lines compute to espresso, `rgb(42, 26, 18)`, so the block follows its section's colour.
- Screenshots at 1280px, 768px and 375px, checked by eye and not committed.
- Console on every run: empty apart from the React DevTools and HMR lines. The second throwaway route read `searchParams` to pick a case, and Next logged its "runtime data during prerendering" error for that route on each load. The error names `/stat-check` and went away with the route.
- After the route was deleted, `/stat-check` returns 404. `/` returns 200; nothing in `app/` or `components/sections/` imports `stat.tsx`. `AGENTS.md` is byte-identical after the runs (`diff -q` against a copy taken before). `grep -l '"use client"' components/site/*.tsx` prints `mobile-nav.tsx` only.

Not run: `npm run build`. The block calls no request API and no `Date`, and #44 runs the build once the section is on the page.

### Review pass

**1. Error and empty states.** The component fetches nothing, so its states are prop values. Four are reachable.

- `label` blank or whitespace: the label line is left out and the number stands alone. Nothing for the visitor to do.
- `value` blank or whitespace: the issue's sketch rendered an empty `<p>` and kept the label's `mt-2`. Measured on the sketch's markup, the empty paragraph is 0px tall and the label starts 8px lower than its neighbours' values. **Fixed.** The value line is left out and the label loses its top margin, so it starts at 0px. An earlier version of this line said the empty paragraph took 48px. That was a guess, and the branch review caught it.
- Both blank: the sketch rendered an empty `<div>` with two empty paragraphs, a blank grid cell. **Fixed.** The block returns `null`. Measured in the stats grid with a blank stat between two others: the sketch's markup leaves an empty 242px cell and the third stat sits at x 660; with `Stat` the grid has two children and the third stat sits at x 378, in the second column. Both props stay required strings, so leaving one off is a `tsc` error.
- One very long word: on the sketch's markup a 45-character value makes the page 811px wide in a 375px viewport and 1068px wide at 768px. **Fixed** with `wrap-anywhere`, measured above.

**2. Type fields rendered by the UI.** `StatProps` has two fields.

| Field | Renders in |
|---|---|
| `value` | the first `<p>`, when not blank |
| `label` | the second `<p>`, when not blank |

Both render. Neither is on the live page today, because nothing imports the block until #44.

**3. Permission gates per route.** Not applicable. The site has one static route, `/`, with no service calls and no auth. The new module reads no request API, so the route stays prerendered.

**5. Left out of scope.**

- The stats section and `app/page.tsx` (#44). Same branch, next commit.
- A value with no space in it. `wrap-anywhere` breaks wherever it must, so `$1,250,000` splits inside the number at 768px (two lines in the 146px column) and is whole at 1280px and 375px. The alternative is overflow, which is worse. None of the four real values is affected; they break at their spaces. Cost of anything better: the grid change #44 already has to consider.
- A fix for the two-line values at 768px. It belongs to the grid, not the block: the options are a later switch to four columns or a smaller value size at that width, and #44 measures the real section before choosing. Cost now: one class, chosen without the heading above it to judge against.
- A `<dl>` for the four stats. Decided against above. Cost: a wrapper element in the section, `dt` and `dd` in the block, and a CSS reorder.
- A `className` prop. The one caller needs none. Cost: one prop and a `cn` call.
- A shared wrapper for blank handling across `SectionHeading`, `FeatureCard` and `Stat`. Each is three lines and renders different elements. Cost: a new helper and three edited files, for less code than it adds.
- `text-balance` or `tabular-nums` on the value. The plan asks for neither and four numbers in separate columns do not need aligned digits. Cost: one class each.
- `next build`. #44 runs it. Cost: about a minute.
